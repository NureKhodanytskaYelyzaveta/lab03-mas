## 1. Тема, мета, зв'язок із кваліфікаційною роботою
Тема кваліфікаційної роботи — ігрове програмне забезпечення у жанрі психологічного горору на Unity. Система «Команда проєктування страшної сцени» (horror-scene-team) за описом сцени готує проєктну документацію: біти й криву страху, звук, візуальні ефекти, репліки внутрішнього голосу для Yarn Spinner. Крива страху (0..1) безпосередньо придатна для `FearLevelController` гри. Задачу потрібно узгодити з викладачем.

Мета: опанувати ADK 2.x, реалізувати систему з ≥3 LLM-агентів із паралельним розгалуженням, обмеженим циклом і детермінованими вузлами, протестувати її з підмінною моделлю та порівняти з одним агентом.

## 2. Чому потрібно кілька агентів (за табл. 1.3 МВ)
| Ознака | Висновок для задачі |
|---|---|
| Ролі і компетенції | Три різні ролі: темп і структура сцени, звук (тиша, стінгери), світло й екранні ефекти. Критерії якості різні |
| Незалежні підзадачі | Звук і візуал залежать лише від сцени й не залежать один від одного → паралельні гілки |
| Перевірка результату | Потрібен незалежний директор, який оцінює сцену разом з обома планами |
| Бюджет | Це етап проєктування, а не реальний час: якість важливіша за кількість викликів |
| Контекст | Звуку й візуалу досить сцени; директору потрібні всі три результати зі стану |

Для задачі без паралельних підзадач і рецензента один агент був би достатній; тут обидві ознаки є.

## 3. Таблиця ролей і граф
Таблиця ролей — розділ 3 файлу `MAS-CARD.md`; граф — `docs/graph.md`. Відповідність коду (`app/agent.py`, `edges`):

| Рядок edges | Стрілки графа |
|---|---|
| `("START", intake)` | START → intake |
| `(intake, {"ok": scene, "reject": reject})` | intake → scene_designer / reject |
| `(scene, scene_check)` | scene_designer → scene_check |
| `(scene_check, {"ok": (audio, visual), "fix": scene})` | паралельне розгалуження / повернення автору |
| `(audio, plans)`, `(visual, plans)` | обидві гілки → JoinNode `plans` |
| `(plans, link_check)` | збирання → перевірка посилань |
| `(link_check, {"ok": director, "fix": scene})` | далі до директора / повернення автору |
| `(director, gate)` | директор → gate |
| `(gate, {"revise": scene, "publish": publish})` | цикл (≤ MAX_DRAFTS) / публікація |

## 4. Контракти даних
`SceneDesign` (title, setting, player_goal, `beats: list[Beat]`, inner_voice_lines), `Beat` (id, description, technique ∈ 8 значень, fear_target), `AudioPlan`/`AudioCue` (beat_id, kind ∈ 5 значень, description, volume), `VisualPlan`/`VisualEffect` (beat_id, effect ∈ 6 значень, intensity, description), `Verdict` (decision ∈ APPROVE/REVISE, comments). Числові межі (0..100, 0..1) навмисно перевіряє код: порушення схеми Pydantic обриває запуск, а вузол повертає чернетку автору з конкретним зауваженням.

## 5. Інструкції агентів і детерміновані вузли
Кожен агент має одну роль і явну заборону чужої роботи («Do not change the beats»). `{request}` і `{feedback?}` у сценариста: запит лишається доступним у циклі, а зауваження на першій чернетці відсутні. Директор бачить `{scene}`, `{audio_plan}`, `{visual_plan}` зі стану. Числові межі: 4–8 бітів, 1–2 підказки на біт, ≤5 зауважень.

| Вузол | Яку відмову запобігає |
|---|---|
| intake | довгі/порожні запити, ін'єкція великим текстом |
| scene_check | порушення контракту: кількість бітів, унікальність id, 0..100, спокійний початок, пік ≥70, розрядка ≥15 |
| link_check | розузгодження: посилання на неіснуючі біти, межі 0..1, біт без звуку й ефекту; каскад: директор не витрачається на зламані плани |
| gate | нескінченний цикл: MAX_DRAFTS = 3 |
| publish | детермінований звіт зі стану, без LLM |
