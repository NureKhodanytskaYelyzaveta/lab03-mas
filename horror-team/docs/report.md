# Звіт з лабораторної роботи № 3
**Мультиагентна система на Google ADK 2.x: графовий робочий процес і координація агентів**

Виконав: Ходаницька Єлизавета Володимирівна, група ПЗПІ-23-3. Репозиторій: https://github.com/NureKhodanytskaYelyzaveta/lab03-mas

## 1. Тема, мета, зв'язок із кваліфікаційною роботою
Тема кваліфікаційної роботи: ігрове програмне забезпечення у жанрі психологічного горору на Unity. Система «Команда проєктування страшної сцени» (horror-scene-team) за текстовим описом сцени готує проєктну документацію: біти сцени з кривою страху, план звуку, план візуальних ефектів і репліки внутрішнього голосу для Yarn Spinner. Крива страху виводиться у форматі 0..1 і придатна для `FearLevelController` гри.

Мета: опанувати Google ADK 2.x; реалізувати систему з ≥3 LLM-агентів із паралельним розгалуженням, обмеженим циклом зворотного зв'язку та детермінованими вузлами; протестувати оркестрацію з підмінною моделлю; порівняти систему з одним агентом.

## 2. Чому задача потребує кількох агентів (за табл. 1.3 МВ)
| Ознака | Висновок для задачі |
|---|---|
| Ролі і компетенції | Три різні ролі з різними критеріями якості: темп і структура сцени, звук (тиша, стінгери, гучність), світло й екранні ефекти |
| Незалежні підзадачі | Звук і візуал залежать лише від сцени й не залежать один від одного, тому працюють у паралельних гілках |
| Перевірка результату | Потрібен незалежний директор, який оцінює сцену разом з обома планами |
| Бюджет | Це етап проєктування, а не гра в реальному часі: затримка некритична |
| Контекст | Звуку й візуалу досить сцени; директору потрібні всі три результати зі стану сесії |

Експеримент (розділ 8) показав, що на обраній моделі виграш у якості не підтвердився; це обговорено у висновках.

## 3. Таблиця ролей і граф
Таблиця ролей: розділ 3 файлу `MAS-CARD.md`. Граф: `docs/graph.md`. Відповідність коду (`app/agent.py`, `edges`):

| Рядок edges | Стрілки графа |
|---|---|
| `("START", intake)` | START → intake |
| `(intake, {"ok": scene, "reject": reject})` | intake → scene_designer або reject |
| `(scene, scene_check)` | scene_designer → scene_check |
| `(scene_check, {"ok": (audio, visual), "fix": scene})` | паралельне розгалуження або повернення автору |
| `(audio, plans)`, `(visual, plans)` | обидві гілки → JoinNode `plans` |
| `(plans, link_check)` | збирання → перевірка посилань |
| `(link_check, {"ok": director, "fix": scene})` | далі до директора або повернення автору |
| `(director, gate)` | директор → gate |
| `(gate, {"revise": scene, "publish": publish})` | цикл (≤ MAX_DRAFTS) або публікація |

Параметри: `MAX_DRAFTS = 3`, `max_concurrency = 2`.

## 4. Контракти даних
- `SceneDesign`: title, setting, player_goal, `beats: list[Beat]`, inner_voice_lines.
- `Beat`: id, description, technique (8 значень), fear_target.
- `AudioPlan` / `AudioCue`: beat_id, kind (5 значень), description, volume.
- `VisualPlan` / `VisualEffect`: beat_id, effect (6 значень), intensity, description.
- `Verdict`: decision (APPROVE або REVISE), comments.

Описи полів (`Field(description=...)`) потрапляють до моделі разом зі схемою. Числові межі (fear_target 0..100, volume та intensity 0..1) свідомо перевіряє код, а не Pydantic: порушення схеми обриває запуск, а детермінований вузол повертає чернетку автору з конкретним зауваженням.

## 5. Інструкції агентів і детерміновані вузли
Кожен агент має одну роль і явну заборону чужої роботи («Do not change the beats»). Шаблон `{request}` лишає запит доступним у циклі, `{feedback?}` необов'язковий (на першій чернетці зауважень немає). Директор бачить `{scene}`, `{audio_plan}`, `{visual_plan}` зі стану. Числові межі: 4–8 бітів, 1–2 підказки на біт, не більше 5 зауважень.

| Вузол | Яку відмову запобігає |
|---|---|
| intake | порожній або надто довгий запит (15–2000 символів), надмірний вхід |
| scene_check | порушення контракту: кількість бітів, унікальність id, fear_target 0..100, спокійний старт (≤30), кульмінація (≥70), розрядка (≥15 нижче піку) |
| link_check | розузгодження ролей: посилання на неіснуючі біти, значення поза 0..1, біт без звуку й ефекту; каскад помилок: директор не витрачається на зламані плани |
| gate | нескінченний цикл: MAX_DRAFTS = 3 |
| publish | детермінований звіт зі стану сесії, без LLM |

## 6. Тести з підмінною моделлю
`uv run pytest -q` → **25 passed** (14 тестів основної системи та 11 тестів кроків 13–14). Тести не звертаються до API.
- щасливий шлях (4 виклики, по одному на агента);
- цикл доопрацювання (REVISE, потім APPROVE; 2 чернетки);
- межа циклу (директор викликається рівно MAX_DRAFTS разів, `stop_reason = max_drafts`);
- невалідна сцена повертається автору без викликів звуку, візуалу й директора;
- зламані посилання на біти повертаються автору до директора;
- короткий запит відхиляється без жодного виклику моделі;
- модульні тести `scene_issues`, `link_issues`, `gate`, `fear_curve`, `render_report`;
- експеримент зі сліпою оцінкою; координатор.

## 8. Експеримент і сліпа оцінка
Модель: `gemini-3.5-flash-lite` для обох систем. 5 запитів (`eval/requests.json`: R1 лікарня, R2 коридор готелю, R3 радіоприймач у підвалі, R4 ліфт, R5 дзеркало). Базова лінія: один агент із тією самою схемою результату. Сліпа оцінка: звіти обох систем перемішані (`eval/blind/`), назва системи і рядок «Рішення» прибрані, оцінку 0–2 поставив здобувач до розсліплення за рубрикою: повнота бітів і кривої страху, відсутність штампів і дешевих jump scare, конкретність звуку й ефектів.

Інтерпретація:
- Очікування методички «команда дає кращий результат» не підтвердилось у сліпій оцінці: якість однакова (1,2 проти 1,2). Команда дає більше деталей (на 17% більше звукових підказок, на 52% більше візуальних ефектів), але на оцінку це не вплинуло.

- Директор у всіх п'яти запусках одразу дав APPROVE (`drafts = 1`), тому цикл доопрацювання в реальних запусках не спрацював. Ймовірна причина: легка модель `flash-lite` у ролі рецензента поблажлива. Цикл перевірено лише тестами.
- Час команди більший лише в 1,5 раза завдяки паралельним гілкам. Час одного агента нестабільний: запуск R4 (21,81 с) схожий на викид через затримку API.
- Пік страху в одного агента вищий (88 проти 81), тобто його сцени «різкіші». Сам по собі це не показник якості.
- Обмеження: 5 запитів, одна оцінювачка/оцінювач, одна легка модель, суб'єктивна рубрика. Висновки орієнтовні.

- Попередження ADK про `context_cache_config` стосується лише кешування промптів між передачами керування і не впливає на результат.
- Порівняння обмежене: координатор відповідає текстом на різні запити, граф будує повну сцену за схемою; вибірка мала (9 запусків).

### Крок 13: база знань із ЛР 2
Додано п'ятого LLM-агента `researcher` з інструментом `search_knowledge` (пакет `kb` із ЛР 2 скопійовано без змін, обгортка в `app/knowledge.py`). Агент зі схемою `output_schema` не може викликати інструменти, тому дослідник не має схеми: його текст з джерелами `[[Нотатка#Розділ]]` записується в стан (`kb_notes`), а `scene_designer` читає його через `{kb_notes?}`. Дослідник стоїть між `intake` і `scene_designer`, тож виконується один раз і не повторюється в циклі доопрацювання. Базу вмикає змінна `OBSIDIAN_VAULT`; без неї граф працює як раніше. Звіт отримав розділ «Нотатки з бази знань». Ціна: вузол виконується один раз, але це два виклики моделі (запит інструмента й підсумок), тож мінімум викликів на запуск зростає з 4 до 6.

### Крок 14: людина в циклі
Після `gate` додано детермінований `risk_check`: сцена ризикова, якщо в плані звуку є не-тиша з гучністю не менше 0,9 (різкий звук у навушниках) або страх у кульмінації не менше 95. Безпечна сцена публікується одразу. Ризикову зупиняє вузол `human_review` (RequestInput зі схемою `HumanDecision`: approved, comment). Відповідь обробляє `human_decision`: схвалено — публікація; відхилено й чернетки лишились — повернення до `scene_designer` з коментарем людини; чернеток немає — публікація зі `stop_reason = human_rejected` і позначкою в звіті. Цикл відхилень обмежений тим самим `MAX_DRAFTS` (тест). У терміналі людина відповідає `y/n` (`run_cli.py`), у Playground запит показує інтерфейс ADK.

Граф із розширеннями наведено на рисунку 10.1 (кольором виділено нові вузли).

Без цих запусків кроки 13–14 підтверджено лише тестами з підмінною моделлю.

## 11. Висновки
Реалізовано мультиагентну систему на графі ADK 2.x: 4 LLM-агенти зі схемами Pydantic, паралельні гілки звуку й візуалу з JoinNode, цикл «створити → оцінити → виправити» з обмеженням `MAX_DRAFTS = 3`, 6 детермінованих вузлів. Оркестрацію перевірено 25 тестами з підмінною моделлю без звернень до API. Два реальні запуски відповідають графу (без повернень по циклах).

Експеримент показав, що на моделі `gemini-3.5-flash-lite` команда не перевершила одного агента за сліпою оцінкою (1,2 проти 1,2), але коштувала у 4 рази більше викликів і в 3,5 раза більше токенів. Цикл у реальних запусках не активувався: директор завжди схвалював із першої чернетки, тож ефект рецензії не виміряно.

Мультиагентну систему варто обирати, коли результат має автоматично інтегруватися в гру (крива страху для `FearLevelController`) і потрібні гарантії узгодженості звуку й візуалу, паралельні незалежні підзадачі та незалежний рецензент. Для швидкої чернетки однієї сцени достатньо одного агента. Координатор підходить для відкритих запитань, але його маршрут нестабільний і не підлягає автоматичній перевірці. Подальші кроки: суворіший рецензент або потужніша модель для директора, більша вибірка запитів, кілька незалежних оцінювачів.

## 12. Примітки щодо відтворюваності
- Запуск 1 виконано на `gemini-3.8-flash`; далі модель довелося змінити на `gemini-3.5-flash-lite` через тимчасову відповідь 503 («high demand») від `gemini-3.8-flash` і `gemini-3.7-flash`. Експеримент і координатор виконано на одній моделі для обох систем.
- Кількість повторів запитів до API збільшено до `attempts=6`.
- Ключ API не потрапив до репозиторію, звіту чи знімків екрана (`.env` у `.gitignore`).
